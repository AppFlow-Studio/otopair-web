Section 1
System Overview
Two forms, two triggers, two purposes. Both feed the Vehicle ID. One happens before the work, one after.
Pre-Job Form
What's on the car right now?

Trigger: Shop taps "Accept" or "Start Job"

Purpose: Confirm or update the vehicle's current specs before work begins

Time target: Under 60 seconds (returning vehicle) · Under 2 minutes (first-time vehicle)

Required: Yes — cannot start job without completing

Post-Job Form
What changed on the car?

Trigger: Shop taps "Complete Job"

Purpose: Report what was done, what parts were used, update the Vehicle ID with any changes

Time target: Under 2 minutes for Part A (mandatory) · Under 1 minute for Part B (optional)

Required: Part A mandatory · Part B optional

Section 2
Pre-Job Form — Complete Question List
These questions appear when the shop accepts a job or taps "Start Job." Designed to be a confirmation screen, not a data entry form. Return vehicles should be one tap. First-time vehicles should take under 90 seconds.
Core principle: The pre-job form collects CONDITION assessments, not specifications. Brand names, part numbers, and detailed specs are collected in the POST-job form when parts are actually being installed. The pre-job just needs to know: what's the mileage, and what condition are the key components in? The system infers the rest.
1
Current mileage
Required Every visit

What the shop sees: "Current odometer reading"

Input type
Numeric input — e.g. "47,230" · Pre-filled with last reported mileage if available
Validation

Must be higher than last reported mileage (flag if lower — possible error). Cannot be empty.

Feeds → Vehicle ID (mileage) · Mileage velocity calculation · Service interval timing · Vehicle Health score
2
Tire condition
Required Every visit

What the shop sees: "Tire condition"

Sub-fields
Front tires — tap selector: Good / Fair / Replace soon
Rear tires — tap selector: Good / Fair / Replace soon
First visit only — additional fields appear
Tire brand — text input (e.g. "Goodyear")
Tire model — text input (e.g. "Wrangler AT")
These only appear if the Vehicle ID has no tire brand data. Once reported, they auto-verify and disappear from future pre-job forms.
Behavior

Tire size is pre-filled from OEM data and shown as read-only context (not an editable field). Run-flat status is a one-time flag from the vehicle data table. The mechanic's job here is a quick visual assessment — two taps — not a spec sheet. Brand/model are collected once and then locked.

Feeds → Vehicle ID (tire condition) · Vehicle Health (tire component) · Tire replacement recommendations
3
Brake condition
Optional Every visit (if on lift)

What the shop sees: "Brake condition (if visible)"

Sub-fields
Front pad thickness — numeric input in mm (e.g. "7") · System auto-classifies: 7+ mm = Good, 4-6 mm = Fair, 3 mm or below = Replace soon
Rear pad thickness — numeric input in mm (e.g. "5") · Same auto-classification
Rotor condition — single dropdown for overall: Good / Scored / Needs attention
Why thickness instead of condition dropdown

A mechanic who can see the brakes can estimate thickness in one glance. The system does the interpretation — the mechanic doesn't need to decide what "Fair" means. This is faster AND more accurate. If they can't see the brakes (car not on lift), they skip this entire section.

First visit only — additional field
Brake pad brand — text input (e.g. "Akebono") · Only appears on first visit if no brake data exists. Collected once, then locked.
Feeds → Vehicle ID (brakes) · Vehicle Health (brake component) · Brake service recommendations · Proactive safety alerts
4
Fluids confirmation
Required First visit — then confirm only

What the shop sees: "Confirm vehicle fluid specs"

First visit
Oil viscosity — shown pre-filled from OEM (e.g. "0W-20") · Shop confirms or edits
Oil type — shown pre-filled from OEM (e.g. "Full Synthetic") · Shop confirms or edits
Coolant type — shown pre-filled from OEM (e.g. "Toyota SLLC") · Shop confirms or edits
Brake fluid — shown pre-filled from OEM (e.g. "DOT 3") · Shop confirms or edits
Return visits (verified data)
Single toggle: "Fluid specs unchanged" — one tap confirms all. Expands to individual fields only if the shop taps "Something changed."
Why this works

Fluid specs rarely change between visits unless a service was performed. For 90% of return visits, this is a one-tap confirmation. The detailed spec editing only surfaces when something is new or different.

Feeds → Vehicle ID (fluids) · Oil change recommendations · Parts pre-population for future jobs
5
State inspection
Optional First visit + when due

What the shop sees: "Inspection sticker"

Sub-fields
Sticker looks current — Yes / No toggle (mechanic can see the sticker on the windshield in seconds)
If Yes: approximate expiry month — month/year picker (e.g. "Sep 2026") · The mechanic reads it off the sticker
If No or expired: "Inspection may be due" flag auto-sets on the Vehicle ID
Behavior

This is NOT asking the mechanic to do a formal check. It's a 5-second glance at the windshield. Once the expiry date is captured, the system handles the reminder cadence (60/30/7 days). On return visits, if the date is already stored and not expiring, this question doesn't appear at all.

Feeds → Vehicle ID (inspection) · Vehicle Health (compliance) · Proactive reminder engine
6
Modifications observed
Optional First visit only

What the shop sees: "Any aftermarket modifications?"

Input type
Single dropdown: None observed / Yes
If Yes → expandable tag selector: Aftermarket exhaust / Lowering springs / Cold air intake / Aftermarket wheels / Tint / Other (free text)
Behavior

Only appears on first visit. If "None observed" is selected, this question never appears again unless a future mechanic flags a modification in their post-job notes. Keeps the form lean for return visits.

Feeds → Vehicle ID (modifications) · Mechanic notes · Future service recommendations
7
Confirm and start
Required Every visit

What the shop sees: "Vehicle specs confirmed" — single button to finalize

Behavior

Logs confirmation timestamp. Marks all confirmed fields as shop-verified. Transitions booking to "In Progress." On return visits where all fields are verified, the entire pre-job form collapses to: mileage input + tire condition taps + this confirm button. Three interactions total.

Feeds → Vehicle ID (verification timestamps) · Booking status → "In Progress"
Section 3
Post-Job Form — Part A (Mandatory)
These questions appear when the shop taps "Complete Job." They MUST be answered before the job can be closed. This is what updates the Vehicle ID with changes made during the service.
Design rule: Part A is context-aware. It only shows questions relevant to the service that was just performed. An oil change job won't ask about brake pads. A tire replacement won't ask about coolant. The system knows what service was booked and tailors the form accordingly.
1
Updated mileage
Required Every job

What the shop sees: "Mileage at job completion"

Numeric input · Pre-filled with pre-job mileage · Shop confirms or updates if car was moved
Feeds → Vehicle ID (mileage) · Service history (mileage at service)
2
Parts installed
Required Every job

What the shop sees: "What parts were used?"

Repeatable section — add as many parts as needed
Part name — text input (e.g. "Oil filter") · Pre-filled from vehicle specs if available
Brand — text input (e.g. "Bosch")
Part number — text input (optional, e.g. "3323")
Cost — currency input (e.g. "$12.50")
[+ Add another part]
Validation

At least one part entry required for services that involve parts. Labor-only services (e.g. diagnostic scan) can skip this.

Feeds → Vehicle ID (current parts on car) · Job actuals (parts cost) · Parts accuracy tracking
3
Vehicle ID updates — what changed?
Required Context-aware

What the shop sees: Context-aware prompts based on the service performed. Only relevant fields appear.

Service → Vehicle ID field mapping
Oil change "Update oil type and viscosity on Vehicle ID?"
Tire replacement "Update tire brand, model, and size on Vehicle ID?"
Brake pad replacement "Update pad brand, type, condition, and rotor condition on Vehicle ID?"
Brake rotor replacement "Update rotor condition and brake service date on Vehicle ID?"
Brake inspection "Update pad condition, thickness, and rotor condition on Vehicle ID?"
Coolant flush "Update coolant type on Vehicle ID?"
Brake fluid flush "Update brake fluid type on Vehicle ID?"
Transmission service "Update transmission fluid type on Vehicle ID?"
State inspection "Update inspection date, result, and emissions status on Vehicle ID?"
Input type

Pre-filled with what was just installed (from Parts Installed section). Shop confirms the Vehicle ID should be updated. If the same part type was used, one tap to confirm. If different from what's on file, the field updates automatically.

Feeds → Vehicle ID (living data layer) · Overrides OEM defaults with real data
4
Mechanic notes — tip for next mechanic
Optional Every job

What the shop sees: "Anything the next mechanic should know about this vehicle?"

Free text area — multi-line
Example notes:
• "Drain plug slightly stripped — use oversized gasket next time"
• "Customer mentioned vibration above 60mph — check wheel balance"
• "Aftermarket exhaust — needs different hangar setup"
• "Customer prefers Castrol Edge oil"
Behavior

Notes are append-only — they never overwrite previous mechanic notes. Each note is timestamped with the mechanic's name and the service date. The full history of notes travels with the car forever.

Feeds → Vehicle ID (mechanic notes) · Visible to every future mechanic at any shop
5
Flag for review
Optional Every job

What the shop sees: "Our vehicle data may be incorrect for this car"

Checkbox: "Flag this vehicle's specs for review"
If checked → optional text: "What's incorrect?" (e.g. "Manual says 0W-20 but car actually needs 5W-30 per owner's manual")
Behavior

Creates an entry in the admin review queue. Waleed investigates and updates the OEM data for this vehicle. Prevents bad data from propagating to other vehicles of the same year/make/model.

Feeds → Admin review queue · Vehicle specs database corrections
Section 4
Post-Job Form — Part B (Optional)
These questions help Otopair optimize its data accuracy over time. The shop can skip them entirely — they don't block job completion. Presented as a simple survey after Part A is submitted.
From the April 18 meeting: Part B is optional. The shop can skip through with "Not available" on anything they didn't do. Only answer questions relevant to the job performed. Think of this as "helping Otopair get smarter" — not a requirement.
1
Actual labor time
Optional

What the shop sees: "How long did this job actually take?"

Numeric input in minutes · Pre-filled with estimated labor time from booking (e.g. "Est. 45 min")
Feeds → Labor time variance tracking · Calibrates future estimates for this service × vehicle combo
2
Difficulty rating
Optional

What the shop sees: "How was this job compared to typical?"

1 — Much easier 2 — Easier 3 — Normal 4 — Harder 5 — Much harder
Feeds → Difficulty calibration per vehicle make/model · Adjusts labor time estimates
3
Parts accuracy
Optional

What the shop sees: "Were the parts we suggested correct for this vehicle?"

Yes — correct No — had to use different parts
If "No" is selected
Free text: "What was different?" (e.g. "Oil filter part # was wrong — correct one is 04152-YZZA1")
Feeds → Vehicle specs accuracy · Corrects parts database for this year/make/model
4
Additional observations
Optional

What the shop sees: "Anything else to report about this vehicle or job?"

Free text area
Examples: "Customer needs to come back for alignment" · "Noticed exhaust leak — unrelated to today's service" · "Recommend brake inspection at next visit"
Difference from mechanic notes (Part A, Q4)

Mechanic notes travel with the Vehicle ID and are visible to future mechanics. Additional observations here feed Otopair's internal optimization and may generate a follow-up recommendation to the user. They're internal signals, not persistent vehicle notes.

Feeds → Internal service recommendations · May trigger a follow-up notification to the user
Section 5
Smart Form Behavior
Rules that make the forms faster and less annoying over time.
Rule 1
Auto-verification: "Answer didn't change"

If a data field has been confirmed by a shop 2-3 times consecutively without changes, it locks as "Verified." On subsequent visits, the field shows as a confirmed badge instead of an editable input. The shop can still tap to override if something changed, but they don't need to re-confirm static data every visit.

Exception: Mileage never auto-verifies — it changes every visit and is always an editable input.

Exception: Tire condition never auto-verifies — it degrades over time and should be re-assessed.

Rule 2
Context-aware post-job: Only ask what's relevant

The post-job form knows what service was performed. An oil change job shows: mileage, parts used, oil viscosity/type update, mechanic notes. It does NOT show: tire updates, brake fluid updates, coolant updates. This prevents the form from feeling overwhelming on simple jobs.

Mapping: Service category → relevant Vehicle ID fields (defined in Section 3, Question 3).

Rule 3
Progressive shortening

A vehicle's first visit = longest form (most fields empty). Each subsequent visit = shorter form (more fields verified). After 3-4 visits, the pre-job form is essentially one tap ("Vehicle specs confirmed") and the post-job form only asks about parts used and mechanic notes. The system rewards repeated use by getting out of the shop's way.

Rule 4
"Not available" skip option for Part B

Every question in Part B (optional) has a "Skip" or "Not available" option. The shop can skip the entire Part B section with one tap: "Skip optimization survey." No guilt, no friction. The data is valuable but never at the cost of shop frustration.
