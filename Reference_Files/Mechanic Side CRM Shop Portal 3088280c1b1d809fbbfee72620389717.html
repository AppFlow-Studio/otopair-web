Overview

Shop owners and mechanics each get their own role-based dashboard on a separate web portal. Shop owners manage everything: shop setup, mechanics, schedules, accept/decline jobs, payouts, job actuals. Mechanics get a focused view: my jobs, my customers, my ratings, complete job actuals for jobs assigned to me.

The portal uses Clerk auth — same system as the user app — but with strict route-level isolation. Regular users (role: "user") who somehow hit the portal URL get redirected to a "This is for shops" page. No crossover.

Shop owners invite mechanics via email. Clerk handles the invitation → account creation flow. A webhook wires it all together so the mechanic's Clerk account, Convex user record, and shop_users junction are created atomically.

Architecture Decisions

Separate Next.js app or route group? Separate Next.js app on a subdomain (e.g., shop.otopair.com). This keeps the consumer React Native app and the shop web portal completely decoupled. They share the same Convex backend and Clerk application but have independent frontends.

Why not one Clerk org per shop? Clerk Organizations add billing complexity and aren't necessary at MVP scale. Instead, we use a shop_users junction table with role-based access checks in Convex. Clerk just handles identity — our backend handles authorization.

Mechanic accounts: Mechanics get real Clerk accounts (not sub-accounts). They log in with email + password or Google OAuth. Their user record has role: "shop_mechanic". A mechanic can be associated with one shop at MVP (multi-shop post-MVP via multiple shop_users rows).

Description:

Invite Flow (Step by Step):

STEP 1: Shop owner clicks "Invite Mechanic" in CRM
    │
    ├── Frontend collects: mechanic's email, role ("mechanic")

    │
    ▼

    │
    ├── Call Clerk Backend API: POST /invitations
    │   {
    │     email_address: "mechanic@email.com",
    │     public_metadata: {
    │       otopair_role: "shop_mechanic",
    │       shop_id: "conv_shop_id_here",
    │       invitation_token: "our_token_here",
    │       mechanic_id: "conv_mechanic_id_here"
    │     },
    │     redirect_url: "https://shop.otopair.com/accept-invite?token=xxx"
    │   }
    │
    ├── Save clerk_invitation_id on our shop_invitations record
    │
    ▼
STEP 3: Clerk sends invitation email
    │
    ├── Email contains: "You've been invited to join [Shop Name] on Otopair"
    ├── CTA button: "Accept Invitation" → redirect_url
    │
    ▼
STEP 4: Mechanic clicks link, lands on shop.otopair.com/accept-invite?token=xxx
    │
    ├── If mechanic has no Clerk account → Clerk sign-up form
    ├── If mechanic already has a Clerk account → Clerk sign-in
    ├── After auth completes, Clerk sets public_metadata from the invitation
    │
    ▼
STEP 5: Clerk webhook fires → Convex HTTP action: handleClerkWebhook
    │
    ├── Event: "user.created" (new mechanic) OR "invitation.accepted"
    │
    ├── Extract from webhook payload:
    │   - clerkUserId
    │   - email
    │   - first_name, last_name
    │   - public_metadata.otopair_role
    │   - public_metadata.shop_id
    │   - public_metadata.invitation_token
    │   - public_metadata.mechanic_id
    │
    ├── If otopair_role exists in metadata (this is a shop invite, not a regular user):
    │   │
    │   ├── Create/update users record:
    │   │   { clerkUserId, email, first_name, last_name, role: "shop_mechanic" }
    │   │
    │   ├── Create shop_users record:
    │   │   { user_id, shop_id, role: "mechanic", mechanic_id, is_active: true }
    │   │
    │   ├── Update shop_invitations: status → "accepted", accepted_at = now
    │   │
    │   ├── Update mechanics record: link any missing data from Clerk profile
    │   │
    │   └── Done. Mechanic can now log in and see their dashboard.
    │
    ├── If NO otopair_role in metadata (regular user signup):
    │   │
    │   └── Standard user creation: { clerkUserId, role: "user", ... }
    │
    ▼
STEP 6: Mechanic is redirected to shop.otopair.com
    │
    ├── Route guard checks: user has shop_users record → allow
    ├── Role check: role === "mechanic" → show mechanic dashboard
    └── Done.

Existing user edge case:
If the invited email belongs to someone who already has an Otopair user account (they're a car owner too), the webhook handles this by:

  1. Finding the existing user by email
  1. Updating their role to "shop_mechanic" (or keeping it if they're already shop staff)
  1. Creating the shop_users junction record
  1. The user now has access to both the consumer app AND the shop portal

Convex HTTP action: handleClerkWebhook

POST /clerk-webhook

Handles events:
- "user.created" → create user record, check metadata for shop invite
- "invitation.accepted" → find invitation by clerk_invitation_id, link user
- "user.updated" → sync profile changes (name, email, photo)

Security:
- Verify Clerk webhook signature using svix
- Reject unsigned or invalid payloads
- Idempotent: re-processing same event doesn't create duplicates

  • Invitation email sent by Clerk with branded template
  • Mechanic can sign up via invite link
  • Webhook correctly processes "user.created" with shop metadata
  • Webhook correctly processes regular "user.created" without shop metadata (no regression)
  • shop_users record created automatically on invite acceptance
  • shop_invitations status updated to "accepted"
  • Mechanic profile linked to user account
  • Existing user invited to shop gets shop_users record without duplicate user creation
  • Webhook signature verification works (rejects tampered payloads)
  • Expired invitations (>7 days) rejected at acceptance
  • Idempotent: webhook replay doesn't create duplicate records
2.3 — Portal Auth Isolation & Route Guards

Type: Full-stack (Web)
Points: 3
Owner: Dev team
Priority: P0 (blocks all portal UI)

Description:
The shop portal (shop.otopair.com) is a separate Next.js web app. It shares the same Clerk application and Convex backend as the consumer app, but has strict route-level protection ensuring only shop staff can access it. Regular users who stumble onto the URL get a clean rejection, not a broken UI.

Auth Architecture:

shop.otopair.com
    │
    ├── Clerk <SignIn /> component (same Clerk app, different redirect)
    │
    ├── After Clerk auth → middleware checks:
    │   │
    │   ├── 1. Is user authenticated? (Clerk session exists)
    │   │   └── No → redirect to /sign-in
    │   │
    │   ├── 2. Does user have a shop_users record? (Convex query)
    │   │   └── No → redirect to /not-authorized
    │   │
    │   ├── 3. What is their role? (from shop_users)
    │   │   ├── "owner" or "manager" → full dashboard access
    │   │   ├── "mechanic" → mechanic dashboard only
    │   │   └── anything else → /not-authorized
    │   │
    │   └── 4. Is shop_users.is_active === true?
    │       └── No → /account-deactivated
    │
    └── Role-based routing:
        ├── /dashboard → shop owner/manager dashboard (2.5)
        ├── /mechanic → mechanic dashboard (2.12)
        ├── /bookings → booking list (owner/manager only)
        ├── /mechanics → mechanic management (owner/manager only)
        ├── /schedule → schedule management (owner/manager only)
        ├── /payouts → payout view (owner only)
        ├── /settings → shop settings (owner/manager only)
        └── /my-jobs → mechanic's job view (mechanic only)

Middleware implementation (Next.js):

typescript

// middleware.ts — runs on every request to shop.otopair.com

export default clerkMiddleware(async (auth, req) => {
  const { userId } = auth();
  
  // Public routes (no auth needed)
  if (isPublicRoute(req)) return;
  
  // Not signed in → redirect to sign-in
  if (!userId) return redirectToSignIn(req);
  
  // Check shop access via Convex
  const shopAccess = await convex.query("shopUsers:getShopAccessForUser", { clerkUserId: userId });
  
  if (!shopAccess) {
    return NextResponse.redirect(new URL("/not-authorized", req.url));
  }
  
  if (!shopAccess.is_active) {
    return NextResponse.redirect(new URL("/account-deactivated", req.url));
  }
  
  // Role-based route protection
  const role = shopAccess.role;
  const pathname = req.nextUrl.pathname;
  
  if (MECHANIC_ONLY_ROUTES.includes(pathname) && role !== "mechanic") {
    return NextResponse.redirect(new URL("/dashboard", req.url));
  }
  
  if (OWNER_MANAGER_ROUTES.includes(pathname) && !["owner", "manager"].includes(role)) {
    return NextResponse.redirect(new URL("/mechanic", req.url));
  }
});

Not-Authorized Page (/not-authorized):

  • Clean branded page (Otopair logo, Primary Blue)
  • "This portal is for Otopair partner shops"
  • "If you're a shop owner, contact us to get started" → link to shop application form
  • "If you're looking for car service, download the Otopair app" → App Store link
  • No broken UI, no error codes, no confusion

Account-Deactivated Page (/account-deactivated):

New shop owner (no shop yet) → Onboarding redirect:

Acceptance criteria:

  • Unauthenticated users → /sign-in
  • Authenticated regular users (role: "user") → /not-authorized
  • Authenticated shop owners → /dashboard
  • Authenticated mechanics → /mechanic
  • Deactivated shop_users → /account-deactivated
  • Role-based route protection enforced (mechanic can't access /payouts, owner can't access /my-jobs)

    • "Add another part" button
  • Difficulty rating (1–5 star selector)
  • Technician notes (multi-line text)

2.10 — Payout & Revenue View

Points: 3 | Priority: P1

Description:
Shop owners see their earnings, pending payouts, and payout history. Data comes from Stripe Connect + internal payments table.

Sections:

  • Summary cards: This month's revenue, pending payout, total all-time earnings
  • Payout history: Table of past Stripe payouts with date, amount, status, bank account last 4
  • Booking revenue breakdown: List of completed bookings with payment amount, platform fee deducted, net to shop
  • Export: CSV download of payout history

Calculation:

  • User pays: total_cost (labor + parts + platform_fee)
  • Platform keeps: platform_fee (5% of labor + parts)
  • Shop receives: total_cost - platform_fee
  • Stripe takes: standard processing fee (~2.9% + $0.30 per transaction)
  • Net to shop: total_cost - platform_fee - Stripe processing

Acceptance criteria:

  • Revenue figures calculate correctly from payments table
  • Payout history pulls from Stripe Connect API
  • Platform fee is clearly shown (transparency principle)
  • Empty state for shops with no completed bookings
  • CSV export works with correct data

Access: Owner only. Managers can view revenue but not payout details (post-MVP permission granularity).
